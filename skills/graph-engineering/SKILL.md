# Graph Engineering

한 에이전트의 루프로는 안 되는 일을, 전문화된 노드들이 공유 상태를 주고받는 그래프로 엮는 설계 원칙이다. 출처는 Shirley, "Graph Engineering Guide (2026)", AI Builder Club (2026-07-20, 2026-08-28 갱신) — https://www.aibuilderclub.com/blog/graph-engineering-guide-2026

**핵심 한 줄:** 이름표는 선택이고, "루프 하나 → 조율된 그래프"로 올라가는 전환만 진짜다. 필요하기 전에는 그래프를 꺼내지 않는다.

## 0. 용어

| 말 | 뜻 |
|---|---|
| 노드 (node) | 일을 하는 단위. 대개 전문화된 에이전트이거나 결정적(deterministic) 단계 |
| 엣지 (edge) | 노드 사이의 경로. 직선, 조건 분기, 팬아웃(여러 갈래로 동시에), 팬인(갈래를 다시 합침) |
| 공유 상태 (shared state) | 엣지를 따라 흐르는 객체. 모든 노드가 읽고 쓴다. 흐를수록 커진다 |
| 루프 (loop) | 에이전트 하나가 목표와 합격선을 받고 스스로 경로를 고르며 반복하는 것 |

**루프는 노드 하나에 자기 자신으로 돌아가는 엣지가 붙은 그래프다.** 그래서 루프에서 그래프로 가는 일은 노드와 엣지를 늘리는 일이다.

**루프와 그래프의 차이는 "누가 경로를 정하나"다.** 루프는 사람이 목표와 합격선만 정하고 경로는 에이전트가 고른다. 그래프는 사람이 유효한 경로와 분기 조건을 선언하고, 에이전트의 자유는 각 노드 **안에서만** 있다.

## 1. 다섯 층 — 그래프는 맨 위층이다

| 층 | 초점 | 묻는 것 |
|---|---|---|
| 1. 프롬프트 | 요청 하나 | 잘 묻고 있나? |
| 2. 컨텍스트 | 모델이 보는 것 | 맞는 정보를 갖고 있나? |
| 3. 하네스 | 도구·메모리·비계 | 행동하고 기억할 수 있나? |
| 4. 루프 | 에이전트 하나의 반복 | 언제 자기 일을 확인하고 멈추나? |
| 5. 그래프 | 여러 에이전트의 조율 | 누가, 어떤 순서로, 어떤 상태를 공유하며 무엇을 하나? |

아래 층이 흔들리면 위층은 그 문제를 키울 뿐이다. 루프 하나가 스스로 검증하며 멈추지 못한다면, 그 루프를 노드로 쪼개도 해결되지 않는다. **루프를 먼저 제대로 만든다.**

## 2. 그래프를 꺼내는 조건

기본값은 **루프**다. 아래 여섯 신호를 하나씩 정직하게 따져 본다. 여섯 개가 다 성립할 필요는 없지만, **대부분이 루프 쪽이면 그래프를 만들지 않는다.** 그때 그래프를 쓰면 두 시간짜리 일이 이틀짜리 프레임워크 공사가 된다. 신호 하나만 걸린다면 루프 안에서 해결할 수 있는지(예: 루프 끝에 검증 단계 추가) 먼저 본다.

1. **과제 모양** — 일이 서로 다른 전문 영역으로 나뉘고 결과를 넘겨준다.
2. **병렬성** — 여러 단계를 동시에 돌리고(팬아웃) 결과를 다시 합쳐야(팬인) 한다.
3. **도구·모델이 다름** — 노드마다 필요한 도구 세트나 모델이 다르다.
4. **제어 흐름** — 역할 사이의 경로를 명시적이고 감사 가능하게 둬야 한다.
5. **실패 격리** — 노드 하나가 망가져도 나머지를 오염시키면 안 된다.
6. **분리된 검증** — 다른 노드의 결과를 따로 검사하는 전담 리뷰어가 필요하다.

**되돌리기 시험:** 노드 몇 개를 에이전트 하나의 루프로 합쳐도 할 수 있는 일이 줄지 않는다면, 합친다.

## 3. 설계 절차 (코드보다 먼저)

1. **루프로 유지할 수 있는지 먼저 시도한다.** 안 되는 이유를 2절 조건 번호로 적는다. 적지 못하면 루프로 간다.
2. **진짜 전문 영역일 때만 노드에 이름을 붙인다.** 기준은 다른 모델, 다른 도구 세트, 또는 읽기 전용 리뷰어다. "요약기", "포매터"처럼 한 루프의 한 단계에 불과한 것은 노드가 아니다.
3. **코딩 전에 엣지를 그린다.** 경로, 조건 분기, 되돌아가는 고리를 스케치한다.
4. **공유 상태 객체를 명시적으로 설계한다.** 노드마다 무엇을 읽고 무엇을 쓰는지 필드 단위로 정한다.
5. **리뷰어 노드에 이빨을 준다.** 작성 노드와 분리된, 읽기 전용 검증자여야 한다. 불합격이면 작성 노드로 되돌리는 조건 엣지가 있어야 한다. 작성자가 자기 결과를 채점하는 구조는 리뷰어가 아니다.
6. **실패를 격리한다.** 한 노드가 실패해도 공유 상태가 오염되지 않게 한다. 쓰기는 자기 필드에만 하고, 실패는 상태에 "실패" 표시로 남기고, 부분 결과를 덮어쓰지 않는다.
7. **틀은 직접 만들지 말고 고른다.** 예: LangGraph, Google ADK, Microsoft Agent Framework. Claude 안이라면 서브에이전트(Agent)와 워크플로 스크립트가 이 틀이다.
8. **지출 상한과 강제 종료 조건을 둔다.** 그래프는 여러 루프가 동시에 도는 구조라, 검증이 약하면 토큰이 병렬로 샌다. 노드 수에 상한을 두고, 되돌아가는 고리마다 최대 반복 수를 두고, 전체 비용 상한을 넘으면 멈춘다.

## 4. 산출물 — 그래프 명세 (구현 전에 이것부터 쓴다)

```
목표: <한 문장>
왜 루프가 아닌가: <2절 조건 번호와 구체적 이유>

노드:
  - <이름>: 하는 일 / 모델 / 도구 / 읽는 필드 / 쓰는 필드 / 읽기 전용?
엣지:
  - A -> B                       (직선)
  - A -> {B1, B2, B3} -> C       (팬아웃 → 팬인)
  - Reviewer --합격--> Ship
  - Reviewer --불합격--> Writer  (최대 N회)
공유 상태: { task, <필드>: <누가 쓰나>, ... }
실패 처리: <노드 실패 시 상태에 무엇을 남기고 어디로 가나>
상한: 노드 <K>개, 지출 $<X>, 고리당 최대 <N>회, 전체 시간 <T>
한 호흡 설명: <그래프 전체를 한 문장으로>
```

"한 호흡 설명"을 못 쓰면 그래프가 너무 크다.

## 5. 기본 골격 — 조사 → 작성 → 검토

```
[Researcher] --{task, notes}--> [Writer] --{task, notes, draft}--> [Reviewer]
                                   ^                                  |
                                   +----------- 불합격 ---------------+
                                                                      | 합격
                                                                      v
                                                                   [Ship]
```

- Researcher는 출처를 모으고 노트를 쓴다.
- Writer는 `{task, notes}`를 받아 초안을 쓴다.
- Reviewer는 `{task, notes, draft}`를 받아 합격선 기준으로 채점한다. 불합격이면 Writer로 되돌린다.
- 상태는 흐를수록 커진다. 각 노드는 받은 상태에 자기 필드를 더해 넘긴다.

## 6. 과잉 설계 경고

| | 예 | 판정 |
|---|---|---|
| 과잉 | "이 PDF 요약해 줘"에 fetcher → chunker → summarizer → reviewer → formatter 다섯 노드 | 루프 하나가 더 빠르고 싸다. 노드들이 다른 모델·도구·검증 역할을 하지 않는다 |
| 적정 | 일일 시장 브리프: researcher가 출처 다섯 곳으로 **병렬** 팬아웃 → synthesizer가 팬인 → writer가 초안 → 회의적인 reviewer가 불합격 시 되돌림 | 각 노드가 루프 하나로는 못 하는 일(병렬 수집, 분리 검증)을 한다 |

**성공 기준은 노드 수가 아니다.** "모든 노드가 루프로는 못 하는 일을 하고, 전체를 한 호흡에 설명할 수 있다"가 기준이다.

## 7. 그래프 엔지니어링이 아닌 것

1. 지식 그래프나 GraphRAG가 아니다. 그것은 데이터 모델링이고, 이것은 실행 모델링이다.
2. 새 능력이 아니다. 방향 그래프와 상태 기계는 오래전부터 있었다(LangGraph, AutoGen GraphFlow, Google ADK 등). 새로운 것은 공통 이름과, 이것을 루프 설계와 다른 설계 기술로 보는 관점이다.
3. 기본 선택지가 아니다. 대부분의 일은 여전히 루프 하나로 끝난다.

## 8. 검토 체크리스트 (설계·리뷰 때 전부 확인)

- [ ] 루프로 안 되는 이유를 2절 조건 번호로 적었고, 여섯 신호 중 대부분이 그래프 쪽인가?
- [ ] 노드마다 다른 모델·도구·읽기 전용 역할 중 하나가 있는가? 없는 노드는 합쳤는가?
- [ ] 엣지(분기·되돌림 고리 포함)를 코드보다 먼저 그렸는가?
- [ ] 공유 상태의 필드별 쓰기 주인이 정해져 있는가?
- [ ] 리뷰어가 작성자와 분리된 읽기 전용이고, 불합격 경로가 실제로 연결되어 있는가?
- [ ] 노드 하나가 실패해도 다른 노드의 결과가 보존되는가?
- [ ] 직접 만든 오케스트레이터 대신 기존 틀을 썼는가?
- [ ] 노드 수 상한, 지출 상한, 고리당 최대 반복, 전체 시간 상한이 코드에 박혀 있는가?
- [ ] 그래프 전체를 한 문장으로 설명할 수 있는가?

하나라도 비면 구현하지 말고 명세(4절)부터 고친다.
