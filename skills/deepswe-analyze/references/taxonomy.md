# 실패 분류 체계

처음 분석에서 쓴 실패 범주 9가지는 이 데이터를 읽어 가며 우리가 직접 만든 것이었다. 이름은 그럴듯했지만 어떤 선행 연구에도 기대지 않은 자체 분류라, 다른 팀의 수치와 나란히 놓고 "우리 모델은 인식 오류가 더 많다"거나 "이건 어느 연구에서도 흔한 유형이다" 같은 말을 할 수 없었다. 그래서 분류 체계를 동료심사를 거친 실증 연구 두 편에서 그대로 가져온 것으로 바꿨다. 이제 실패 원인(root cause)과 실패 이후 행동(post-failure behaviour)은 CLI 코딩 에이전트 궤적을 분석한 arXiv 2607.09510의 분류를, 실패가 일어난 단계(phase)는 자동 이슈 해결 실패를 분석한 arXiv 2509.13941의 분류를 쓴다. 판정 항목이 늘어난 것이 아니라, 같은 것을 남들과 비교 가능한 이름으로 부르게 된 것이다.

## 실패 원인 (root cause) — 9가지 중 하나

**인식 오류 (epistemic) — 에이전트가 그린 세상의 그림이 틀렸다**

- `false_premise` — 과제나 환경에 대해 확인하지 않은 가정 위에서 행동한다
- `specification_neglect` — 명시적으로 적힌 요구사항을 무시하거나 잊는다
- `output_misreading` — 명령 출력이나 오류 메시지를 잘못 해석한다
- `ignored_signal` — 자기 가정과 어긋나는 증거를 보고도 그대로 진행한다
- `premature_action` — 기본적인 확인도 하지 않은 채 먼저 손을 댄다

**역량 부족 (competence) — 무엇을 해야 할지는 알았지만 해내지 못했다**

- `knowledge_gap` — 필요한 도메인·도구·라이브러리·프로토콜 지식이 없다
- `capability_limitation` — 전략은 합리적이었으나 실행을 틀리게 했다

**외부 요인 (external)**

- `environment_blocker` — 외부 환경 문제에 막혀 실패한다
- `verifier_artifact` — 해법 자체는 방어 가능한데 채점기 쪽 관례에 걸려 거부됐다(이름 충돌, 테스트 id 순서, 숨겨진 테스트의 기대값)

## 실패 단계 (phase) — 3가지 중 하나

- `localization` — 결정적 실수가 "고칠 코드를 찾는" 데서 났다
- `repair` — 결정적 실수가 "고친 내용" 자체에 있었다
- `validation` — 결정적 실수가 "결과를 확인하는" 데서 났다

## 실패 이후 행동 (post-failure behaviour) — 6가지 중 하나

- `gives_up` — 별다른 작업 없이 곧바로 종료한다
- `repairs_wrong_problem` — 실제 원인이 아닌 것을 계속 고친다
- `repeats_same_approach` — 방향을 바꾸지 않고 같은 실패 전략을 되풀이한다
- `useless_checks` — 결과를 더 이상 바꿀 수 없는 검증을 계속 돌린다
- `fabricates_success` — 과제가 안 풀렸는데 성공했다고 주장하거나 자기 테스트를 느슨하게 고친다
- `none_reached` — 그런 구간 없이 제출에서 실행이 끝났다

## 출처

- **"Failure as a Process: An Anatomy of CLI Coding Agent Trajectories"**, arXiv 2607.09510 (<https://arxiv.org/html/2607.09510>) — 실패 원인과 실패 이후 행동을 가져왔다. 이 연구는 Claude Opus가 초안을 쓰고 사람 주석자 두 명이 확정하는 방식으로 라벨을 붙였고, Cohen's kappa는 0.78~0.94였다. 이들이 보고한 분포는 인식 오류 57.9%, 역량 부족 32.8%, 환경 9.4%다.
- **"An Empirical Study on Failures in Automated Issue Solving"**, arXiv 2509.13941 (<https://arxiv.org/abs/2509.13941>) — localization / repair / validation 세 단계를 가져왔다. 3단계·9범주·25하위범주로 된 분류 체계이며, 연구자 네 명이 실패 사례 150건을 둘씩 독립 코딩했고 쌍별 kappa는 0.72~0.77이었다.
- **"SWE-EVO"**, arXiv 2512.18470 (<https://arxiv.org/pdf/2512.18470>) — 참고만 했다. 여기 쓰인 7개 범주는 더 거칠어서 위 분류 안으로 포개진다.

## 우리가 더한 것

`verifier_artifact` 하나는 우리가 추가한 범주다. 위 아홉 중 유일하게 선행 연구에 없다. 모델의 해법이 그 자체로는 방어 가능한데 채점기 쪽 관례 때문에 거부되는 경우가 실제로 있었고(이름 충돌, 테스트 id 순서, 숨겨진 테스트의 기대값), 이것을 모델의 인식 오류나 역량 부족으로 접어 넣으면 개선해야 할 지점을 잘못 가리키게 된다. 그래서 별도로 두고, 이 범주가 붙은 건은 학습 데이터 보강 대상이 아니라 채점 환경 점검 대상으로 다룬다.

## 한계

- 라벨은 원본 트랜스크립트가 아니라, 앞선 판정 단계에서 뽑아 둔 근거(인용된 reasoning, 결정적 명령, 패치 차이)를 보고 붙였다. 트랜스크립트에는 있었지만 그 근거에 담기지 않은 정보는 반영되지 않았다.
- 전체 라벨링은 모델 하나가 했고, 두 번째 모델은 일부 표본에만 라벨을 붙여 일치도를 재는 데 썼다.
- 사람이 최종 판정한 건은 없다. 위 두 연구가 사람 주석자로 확정한 것과 달리, 여기 숫자는 사람 검수를 거치지 않았다.
- 일치도 측정 결과 (2026-09-08). 전체 170건은 Sonnet이 라벨을 붙였고, 그중 60건을 Opus가 같은 기준으로 독립 판정했다. 서로의 답을 보지 못한 상태였다.

| 축 | 일치율 | Cohen's kappa |
|---|---|---|
| 근본 원인 (9종) | 75% | 0.67 |
| 단계 (3종) | 92% | 0.75 |
| 실패 뒤 행동 (6종) | 63% | 0.29 |

단계 축은 선행 연구가 보고한 0.72~0.77과 같은 수준이다. 근본 원인은 0.67로 그보다 조금 낮은데, 관례적 기준인 0.6은 넘는다. 불일치는 특정 짝에 몰린다. 신호 무시와 잘못된 전제 사이, 잘못된 전제와 사양 무시 사이다. 둘 다 "확인하지 않았다"와 "알고도 넘어갔다"의 경계이고, 궤적만으로는 갈리기 어려운 지점이다.

실패 뒤 행동은 0.29로 신뢰하기 어렵다. 이 축은 사이트에서 참고용으로만 표시하고 결론의 근거로 쓰지 않는다. 원인은 두 가지로 보인다. 판정을 궤적 원문이 아니라 앞선 판정자가 추출한 증거에서 했기 때문에 실패 이후 구간의 정보가 얇고, 여섯 범주의 경계가 서로 겹치기 때문이다. 제대로 재려면 궤적 원문을 직접 읽어 다시 라벨해야 한다.

## localization 3%는 오분류인가 — 표적 재판정 (2026-09-08)

단계 분포가 repair 131 / validation 33 / localization 5로, 2509.13941에서 큰 몫이던 localization이 3%뿐이라 판정자가 localization을 repair로 접어 넣었는지 확인했다. Sonnet 라벨을 가장 의심할 만한 55건을 골랐다. 정답 패치가 고친 파일의 절반도 건드리지 않았는데 localization이 아닌 44건, 확신도 low 11건, 기존 localization 5건(중복 제거). Opus에 2509.13941의 단계 정의와 "모델이 안 건드린 정답 파일이 실패 테스트에 필수였는가"를 명시해 독립 판정시켰다.

| | |
|---|---|
| 일치 | 47 / 55 (85%), Cohen's kappa 0.67 |
| 뒤집힘 | validation→repair 7, repair→localization 1 |
| 보정 후 분포 | repair 137 / validation 26 / localization 6 |

localization을 찾으라고 유도한 표본에서도 새로 나온 것은 1건이다. 정답 파일 적중률이 낮은 44건은 대부분 정답과 다른 파일에서 유효하게 풀려다 내용을 틀린 repair였다. 즉 파일 적중률은 localization의 지표가 아니고, **이 벤치마크에서 localization이 드문 것은 분류 오류가 아니라 실제다.** 기능 추가 위주라 어디를 고칠지는 지시문이 거의 알려 주기 때문으로 보인다. 오히려 작은 편향은 반대쪽에 있었다. validation으로 붙은 33건 중 7건은 Opus가 repair로 봤다. 검증을 안 한 것은 맞지만 검증했어도 고칠 수 없는 패치였다는 판단이다.

사이트의 라벨은 Sonnet 원본을 유지한다. 판정자를 섞지 않기 위해서다. 판정 파일은 `jobs/analysis-crosscheck/phase-recheck/`에 있다.
